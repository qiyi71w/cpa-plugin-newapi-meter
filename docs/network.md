# 代理、重定向与日志

[返回 README](../README.md)

## 代理选项

每个账户单独选择访问站点的方式。概况、详情、测试连接、自定义查询和测试脚本的请求都按这个选项发出；测试连接和测试脚本用表单里当前选的选项。

- **跟随 CPA 代理**（默认）：插件把请求交给 CPA，由 CPA 发出（插件宿主的 `host.http.*` 回调），使用 CPA 配置里的 `proxy-url`。CPA 没有配置 `proxy-url` 时，请求和 CPA 自己的其他请求一样：没有代理环境变量就直连；CPA 进程设置了 `HTTP_PROXY` / `HTTPS_PROXY`（以及 `NO_PROXY`）时按它们走。CPA 凭据文件上单独设置的代理不用于插件的请求。
- **直连**：插件用自己的 HTTP 客户端直接访问站点，不使用任何代理：既不用 CPA 的 `proxy-url`，也不读 `HTTP_PROXY` / `HTTPS_PROXY` 等环境变量。适合不需要绕代理的站点。

两种方式的时限、响应上限和失败分类相同：内置来源每个请求 15 秒、响应最大 8 MiB；自定义查询的整个查询 10 秒（请求、脚本运行和插件处理脚本结果都算在内）、响应最大 1 MiB。跟随 CPA 代理时，时限由插件计时，到时插件让 CPA 取消还在进行的请求；响应边接收边计数，超过上限就停止接收。

> [!CAUTION]
> 站点是 http（不是 https）地址时，所用代理能看到完整的请求，包括请求头里的凭据。

## 站点重定向到其他地址时

凭据只应发给账户配置的站点。站点返回重定向（3xx）时，两种方式的处理不同。

### 直连

只跟随仍在同一站点的重定向：协议、主机和端口都不变，或者同一主机从 http 升级到 https（默认端口 80 到 443）。

- 域名按实际连接用的和实际发送（请求头 `Host`）的 ASCII 形式比较，两种形式都相同才算同一主机，英文字母不区分大小写。例如 `例子.com` 和 `xn--fsqu00a.com` 连接和发送的都是 `xn--fsqu00a.com`，算同一主机；`é.example` 和 `É.example` 连接的是同一个地址，但发送出去的形式不同，算不同主机。无法转换成 ASCII 形式的域名一律不跟随。
- IP 地址按地址本身比较，IPv6 的写法差异（字母大小写、省略的 0）不影响结果，但带区域标识（`%` 后的网卡名）时，区域标识必须完全相同；IP 地址和域名之间一律算不同主机。
- 重定向到其他主机或端口，或者任何一跳从 https 回到 http（包括先升级到 https 又降回 http），插件都不跟随，也不向那个地址发任何请求；这次查询按收到的重定向响应判为失败：响应是网页时显示为「站点防护拦截」，否则显示为「响应异常」。

站点迁到新域名后，请把账户的站点地址（自定义查询的 `baseUrl`）改成新地址。

### 跟随 CPA 代理

重定向由 CPA 跟随，插件无法阻止。插件给每个请求设置只含站点来源的 `Referer`（例如 `https://newapi.example.com/`），原请求 URL 里的 query 不会经 `Referer` 带到新地址；脚本自己设置了非空的 `Referer` 时保留脚本的值，设成空值时按没有设置处理。CPA 在重定向时会去掉哪些请求头，取决于 Core 版本：

- **v8.0.42 及以上**：跳到其他来源时，CPA 去掉名称像凭据的请求头：`Authorization`、`Proxy-Authorization`、`Cookie`、`Cookie2`、`WWW-Authenticate`，以及名称含 `token`、`secret`、`api-key`、`apikey`、`api_key`、`credential` 的头。CPA 判断是否为其他来源时比较协议、端口和主机名，主机名按 Unicode 规则忽略大小写，因此只有大小写折叠后仍然不同的主机名才算其他来源。即使在这些版本上，以下内容仍会随重定向发往新地址：
  - 名称不像凭据的请求头，例如内置来源的 `New-Api-User`（用户 ID），以及脚本里自定义名称的头（如 `X-User`）；
  - 307/308 重定向时的请求体；
  - 站点自己写进重定向地址里的内容，例如迁移后保留原路径和 query 的重定向，会把 query 里的值带过去。
- **v8.0.0 到 v8.0.41**：CPA 按 Go 的默认规则跟随重定向，只去掉两类请求头：一类是 `Authorization`、`Cookie`、`Cookie2`、`WWW-Authenticate`、`Proxy-Authorization`、`Proxy-Authenticate` 这些认证头，只在跳到另一个主机、而且不是原主机的子域名时才去掉；另一类是 301/302/303 重定向不再发送请求体时，描述请求体的 `Content-Type`、`Content-Encoding`、`Content-Language`、`Content-Location`。Go 拿每一跳和最初请求的主机比较，比较时区分英文字母大小写，所以只差大小写的主机名也算另一个主机；认证头在某一跳被去掉后，后面的跳转即使回到原主机也不会再带上。不属于这两类的请求头会带过去，包括 `X-Api-Key` 这类名称像凭据的头、`New-Api-User` 和脚本里的其他头。同一主机只换端口或协议，或者跳到原主机的子域名时，`Authorization` 也会带过去。上面列出的 307/308 请求体和重定向地址里的内容同样会发往新地址。

> [!IMPORTANT]
> 使用 v8.0.0 到 v8.0.41 时，建议给账户选「直连」，或者把 Core 升级到 v8.0.42 及以上。

在 v8.0.42 及以上的 Core 上，自定义查询脚本应把密钥放在 `Authorization` 或名称含 `token`、`api-key` 等的请求头里。不放心站点会重定向到别处时，可以给账户选「直连」。

v8.0.42 是按上游源码确认的、最早带这条剥离规则的版本，相关行为在 CPA Core v8.0.78 上实测过；v8.0.0 到 v8.0.41 的说明来自上游源码和 Go 的重定向规则，没有在宿主里实测。

## CPA 的 request-log 会不会记下凭据

不会。我们在 CPA Core v8.0.78 上开启 `request-log` 和 `logging-to-file` 核对过（另做了一轮再加开 `debug` 的核对）：经「跟随 CPA 代理」发出的内置来源请求（请求头里的 PAT、旧版访问令牌和 `New-Api-User`）和自定义查询请求（分别放在请求头、URL query 和请求体里的值），在 CPA 的日志目录和控制台输出里都找不到。

原因是这些请求由插件的管理路由发出，而 CPA 的 request-log 不记录管理路由，也没有记录管理路由里发出的插件请求；页面调用管理路由时提交的凭据（例如测试连接）同样不会被记录。CPA 的访问日志只记一行管理路由的方法、路径和 query（插件的管理路由不在 query 里放凭据）。

这个结论只在 CPA Core v8.0.78 上核对过，其他版本的日志行为可能不同。
